## 1. Principles
1. **Money and stock are proven, not eyeballed.** Every posting rule has a test asserting the exact journal lines, that debits equal credits, and the exact stock movement.
2. **The test pyramid:** many fast unit tests of domain services; feature/API tests against a real MySQL 8.0, never SQLite, because CHECK constraints, row locks and decimal behaviour must match production; a small set of end-to-end journeys.
3. **No fake backends in the product.** Frontend component tests may use MSW mocks. Integration and E2E always run against the real Laravel API and a seeded database.
4. **Tests are traceable:** each test name starts with its ID (`test_TC_SAL_004_posting_creates_balanced_journal`).
5. **Regressions get a test first:** every bug fix starts with a failing test that reproduces it.

## 2. Tooling
| Layer | Tool |
|---|---|
| Backend unit and feature | PHPUnit 11 (or Pest 3) with Laravel testing helpers, `RefreshDatabase` using transactions, model factories |
| Static analysis | PHPStan level 8 (Larastan), Laravel Pint; a custom rule bans `float` casts and arithmetic operators on money in `app/Domain` (money goes through `Money`/`brick/math`) |
| Contract | `openapi.yaml` validated in CI; `league/openapi-psr7-validator` middleware in tests checks every request and response against the spec |
| Database | Migrations run on MySQL 8.0 in CI (Docker service); a schema-dump diff after up/down/up |
| Frontend unit and component | Vitest + React Testing Library + MSW; axe-core via `vitest-axe` |
| End-to-end | Playwright against docker-compose (API + MySQL + SPA) seeded with the demo company |
| Performance | k6 scripts with a 1M-line generated dataset |
| Security | OWASP ZAP baseline against staging; `gitleaks` on repo and bundle; `composer audit`, `npm audit` |

## 3. Unit testing
Targets: `Money`, `DocumentCalculator` (BR-010/011/012), `AverageCostCalculator` (BR-017), `JournalBuilder` (BR-001/002), `AllocationPlanner` (oldest-first, BR-020), `LcStateMachine` (BR-040), `LandedCostAllocator` (BR-045), `NumberFormatter` (lakh/crore, words), `PermissionResolver`. Pure PHP, with no database. Property-based tests (`eris`/hand-rolled generators) throw random documents at the posting rules and assert balance.

## 4. Backend feature and API tests
One test class per endpoint group. Each endpoint gets: a happy path; validation failures; a permission matrix (generated by iterating the `x-permission` of every operation in `openapi.yaml`, for every seeded role); company isolation (another company's ID returns 404); and idempotency for endpoints with `Idempotency-Key`.

## 5. Frontend component tests
Design-system components (Amount, DataTable, Field, BalanceStatus, Dialog) are tested against token values in both themes. Forms are tested for 422 error mapping. The invoice editor is tested to display `/calculate` results only. Protected routes, keyboard shortcuts, and the responsive snapshots at 1440/1200/1024/390 are covered.

## 6. Integration tests
Concurrency (parallel PHP processes against MySQL), queue jobs (exports, statement e-mails, recurring drafts, backups), scheduler (period-lock reminders, LC expiry alerts), file storage (S3-compatible MinIO in CI), mail (Mailpit).

## 7. Database constraint tests
Every CHECK, UNIQUE and FK in [04](04-Database-Design.md) is exercised directly with SQL inserts that must fail (TC-DB-*). The posted-line immutability trigger is tested (TC-ACC-003).

## 8. Accounting balance and inventory consistency suites
After **every** feature test, a `BooksAreConsistent` assertion trait runs:
- Σdebit = Σcredit over posted lines;
- each document's `journal_entry_id` entry balances and has `source_type/source_id` pointing back to it;
- `stock_balances` = Σ(movements in − out) per product and warehouse;
- `stock_balances.total_value` = Σ(value_in − value_out) per product and warehouse;
- the inventory group balance in the ledger = stock valuation (when there are no unallocated landed-cost differences);
- `balance_due` = total − Σ live allocations for every invoice and bill.

The same checks run nightly in production (NFR-042).

## 9. Concurrency and duplicate-submission tests
TC-CON-001…005: parallel stock depletion, parallel allocation, double-click with the same Idempotency-Key, connection loss mid-transaction, and the deadlock-ordering probe. They are implemented with `pcntl_fork` or Symfony Process workers hitting the HTTP kernel against a shared MySQL database.

## 10. End-to-end workflow tests and regression
Seven Playwright journeys (TC-E2E-001…007) mirror the six designed journeys plus the import/LC flow. They run on every merge to `main` and nightly on staging. **Regression:** the full backend suite and the E2E smoke run on every pull request; the full E2E, performance and ZAP scans run nightly; a release candidate needs all green and a manual exploratory pass using the checklist in [10 §4](10-Development-Roadmap.md).

**Coverage gates:** Domain layer ≥ 85% lines; posting services 100% of rules covered by balance tests (NFR-061); frontend components ≥ 70%.

**Acceptance criteria for a test phase:** zero failing tests; no open Severity 1/2 defects; each FR of the release shows only passing tests in the traceability matrix ([01 §16](01-SRS.md#16-traceability-matrices-ui-page--action--api--service--tables--rules--tests)).
